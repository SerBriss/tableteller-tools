# M3.2 PC Skills Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The PC's skills shift `fate_check` odds: the campaign stores `pc_skills` as text, the DM passes a `shift` and a `reason`, and the server moves the odds, logs the shift and says so in the reply only when the shift changed the answer.

**Architecture:** `pc_skills` is one new text column on `campaign`, shown in the brief and the recap and changed with a new `campaign_update` tool; the server never parses it. `OddsLevel.shifted` moves the odds with the clamping rules, and `FateService` reads one d100 roll at both the given and the shifted odds. `OracleTools.fateCheck` takes `shift` and `reason`, adds `shift_effect` and one summary sentence only when the two answers differ, and logs every non-zero shift. The prompts and the system prompt tell the DM how to fill `pc_skills` and when to shift.

**Tech Stack:** M3.1's stack, unchanged: Java 21, Spring Boot 4.1.1, Spring AI 2.0.1 (MCP SDK 2.0.0), Jackson 3, Flyway, PostgreSQL 16, JUnit 5 + AssertJ, Testcontainers. No new dependencies.

**Spec:** `docs/SPEC.md` (v0.8). Read "Shifts" (Oracle tools), the `fate_check` and `campaign_*` rows, "PC skills" and the system prompt rules (Session protocol and DM prompt), the `character_sheet` and `new_campaign` prompts, and the v0.8 decisions before starting.

**Branch:** a worktree branch cut from `master`.

## Global Constraints

- Every M1–M3.1 constraint still holds: run Gradle with `JAVA_HOME=/c/Users/sefim/.jdks/corretto-21.0.10`; Docker must be running; all randomness goes through `RandomSource.between`; every oracle tool writes exactly one roll-log row; bad input throws `IllegalArgumentException` whose message says what is wrong and what is allowed; no `@SpringBootTest`; no text from published games in the repo.
- Do not run `bootJar` and do not touch `build\libs`: Claude Desktop runs that jar and locks it.
- A tool checks its own input before it resolves `campaign`, so input errors come before campaign errors and a rejected call writes nothing.
- Parameter names are the tools' wire names: `pc_summary` and `pc_skills` stay snake_case.
- `pc_skills` is stored and returned exactly as given; the server never parses, trims or validates its content.
- A `fate_check` without a shift (`shift` omitted or 0) returns and logs exactly what it does today, and ignores `reason`.
- A shift is a whole number from −8 to 8; summaries write it with its sign, `%+d` (`+1`, `-2`).
- Summaries and messages other than the ones this plan lists do not change.
- `tools/list` grows from 18 to 19 tools (`campaign_update`); `prompts/list` from 4 to 5 (`character_sheet`).

## Review Focus

1. **A shift that changes nothing leaves the reply as it is today**, so the DM narrates it like any roll; the roll log still records it. Test: Task 3 `aShiftThatChangesNothingLeavesTheReplyAsItIs`.
2. **Cyrillic reasons over stdio:** the playtests are in Russian, so `"reason": "Ловкость +3"` must come back intact in the summary and in `roll_history`. Test: Task 3 `fateCheckShiftsOverStdio`.
3. **Shifts at the ends of the scale:** `nearly_certain` +3 becomes `certain` and the summary still says `+3`; `certain` −8 stays `certain` and the reply says nothing. Test: Task 3 `shiftsStopAtTheEnds`.
4. **A converted sheet is long and multi-line:** a 41-line `pc_skills` with Cyrillic keeps every newline through `campaign_update`, the brief, the brief resource and the recap. Test: Task 2 `aLongSheetSurvivesTheBriefAndTheRecap`.
5. **The DM sends `""` for the field it means to keep:** a blank field in `campaign_update` leaves that field as it is. Test: Task 2 `blankFieldsAreLeftAsTheyAre`.

### Task 3: Shifts on fate_check

**Files:**
- Modify: `table/OddsLevel.java`, `table/FateAnswer.java`, `fate/FateOutcome.java`, `fate/FateService.java`, `tools/OracleTools.java`, `StdioEndToEndTest.java`, `ScriptedSessionTest.java`
- Create: `src/test/java/dev/tableteller/table/OddsLevelTest.java`
- Test: `fate/FateServiceTest.java`, `tools/OracleToolsTest.java`

**Interfaces:**
- Produces: `OddsLevel.shifted(int levels)`: `impossible` and `certain` return themselves; any other level moves `levels` steps by ordinal and stops at `impossible` or `certain`.
- Produces: `FateAnswer.withArticle()`: `a yes`, `a no`, `an exceptional yes`, `an exceptional no`.
- Produces: `FateOutcome(int roll, FateAnswer answer, boolean randomEventTriggered, OddsLevel shiftedOdds, FateAnswer withoutShift)` with `boolean shiftChangedTheAnswer()` (`answer != withoutShift`). `answer` is read at `shiftedOdds`, `withoutShift` at the given odds, both from the same roll.
- Produces: `FateService.check(FateChart chart, OddsLevel odds, int shift, int chaosFactor)`; the three-argument `check` stays and calls it with shift 0. The random-event trigger depends only on the roll and chaos, as before.
- Produces in `OracleTools`: `public record ShiftEffect(OddsLevel odds, @JsonProperty("without_shift") FateAnswer withoutShift)`, and `FateCheckResult(String rollId, FateAnswer answer, List<Integer> dice, int chaosFactor, boolean randomEventTriggered, RandomEvent randomEvent, @JsonProperty("shift_effect") @JsonInclude(JsonInclude.Include.NON_NULL) ShiftEffect shiftEffect, String summary)`.
- Produces: `OracleTools.fateCheck(String campaign, String question, OddsLevel odds, Integer shift, String reason)`:
  - description: "Ask the oracle a yes/no question about the story. Pick honest odds for an ordinary capable person; for the player character's own action, pass the shift its pc_skills give and name it in reason. The server rolls d100 on the fate chart at the current chaos factor and reports whether a random event triggered. Narrate the answer faithfully and never reroll."
  - `shift`: optional, "Levels to move the odds for the player character's own action, from the campaign's pc_skills: -8 to 8; omit for none"
  - `reason`: optional, "What the shift comes from, for example Athletics +4; required when shift is not 0"
  - Checks, in order after `question` and `odds`: `shift must be -8 to 8; got 9`; then, for a non-zero shift with a null or blank reason, `reason must not be blank when shift is not 0; say what the shift comes from, for example "Athletics +4"`.
  - Shift null or 0: the call is exactly today's; `reason` is not stored.
  - Non-zero shift: row `inputs` are `question, odds, shift, reason` (reason trimmed); row `result` is `answer, shifted_odds, without_shift, chaos_factor, random_event_triggered` and `random_event` when one fired. This holds whether or not the shift changed the answer.
  - When `shiftChangedTheAnswer()`: `shiftEffect` is `new ShiftEffect(shiftedOdds, withoutShift)`, and the summary is `"%s (%d on %s %+d, chaos %d). %s turned %s into %s."` (answer label, roll, given odds, shift, chaos, reason, `withoutShift.withArticle()`, `answer.withArticle()`), followed by the random-event sentence when one fired. Otherwise `shiftEffect` is null and the summary is today's.

The demo chart values the tests rely on (yes / exceptional yes / exceptional no from): likely at chaos 4 is 60 / 12 / 93, very_likely at chaos 4 is 75; likely at chaos 5 is 65 / 13 / 94, very_likely at chaos 5 is 80 / 16; likely at chaos 6 is 70, unlikely at chaos 6 is 40 / 8 / 89; nearly_certain at chaos 5 is 90, certain at chaos 5 is 95.
